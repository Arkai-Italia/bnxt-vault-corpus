# Wrench-AI

Ask questions about your motorcycle and get answers pulled straight out of the owner's manual, with the page number attached.

Owner's manuals are 200 pages of tiny print, and the one thing you need (tire pressure, oil capacity, chain slack) is always buried three sections deep. Wrench indexes the PDF and answers in plain English. If it isn't in the manual, it says so instead of guessing.

[](https://github.com/shayyan24/wrench-ai/blob/main/Wrench-ai-ss.jpg)

The bike diagram up top is a bit of fun: it keyword-matches your question and lights up whatever part you're asking about. Ask about tire pressure, the wheels glow orange, in this case asking about chain slack highlights the chain.

## How it works

Standard RAG setup:

1. **`ingest.py`** — reads every PDF in `Manuals/`, pulls the text page by page, splits it into ~800 character overlapping chunks, and stores them in a local Chroma database. Each chunk remembers which file and page it came from.
2. **`rag.py`** — embeds your question, pulls the 4 closest chunks, and hands them to Claude with instructions to answer *only* from that text and cite the page.
3. **`app.py`** — the Streamlit UI.
4. **`bike.py`** — the SVG diagram and the keyword map behind the highlighting. No AI involved, just regex.
5. **`eval.py`** — scores how often retrieval returns the chunk with the answer. See [Evaluation](https://github.com/shayyan24/wrench-ai/blob/main/README.md#evaluation).
6. **`judge.py`** — an LLM-as-judge. Hands an answer, its question and the chunks it was built from to a stronger model and asks whether it holds up.
7. **`eval_answers.py`** — scores the answers themselves, using the judge. See [Judging the answers](https://github.com/shayyan24/wrench-ai/blob/main/README.md#judging-the-answers).

There's a **"Use RAG" toggle** in the UI. Turn it off and the same question goes to the model with no manual context, which is the fastest way to see why grounding matters — you'll get an answer that sounds just as confident and is often wrong about the specific bike.

The example manual bundled here is a 2018 Honda CBR500R. Drop any other manual into `Manuals/` and re-run the ingest to switch bikes.

## Running it

You'll need Python 3.10+ and an [Anthropic API key](https://console.anthropic.com/).

```
python -m venv venv
venv\Scripts\activate          # Windows
source venv/bin/activate       # macOS/Linux
pip install -r requirements.txt
```

Make a `.env` file in the project root:

```
ANTHROPIC_API_KEY=sk-ant-...
```

Then build the index and start the app:

```
python ingest.py               # ~1 min, prints how many chunks it stored
streamlit run app.py
```

It opens at <http://localhost:8501>.

The `chroma_db/` folder is gitignored since it's regenerated by `ingest.py`. Retrieval itself runs locally, so even without an API key you can still see which manual pages a question pulls up — you just won't get the written answer.

## Evaluation

`eval.py` scores retrieval on its own. If the right chunk never comes back, the prompt can't save it.

```
python eval.py
```

16 questions with answers taken off the CBR500R spec tables, scored two ways:

* **page hit@4** — was any retrieved chunk from a page holding the answer?
* **value hit@4** — did a chunk actually contain the answer text? Stricter, since the page can come back while the ~800 character chunk with the number gets missed.

Gold pages aren't hand-written, they're found by scanning the index for the answer string. It runs offline, so it's free to re-run whenever chunk size or `k` changes, and exits non-zero below 75%.

[](https://github.com/shayyan24/wrench-ai/blob/main/eval.jpg)

Scoring is substring matching, so it only proves the number reached the model, not that the model used it right. Chain slack, idle speed and cooling capacity still miss. Scoring the answer itself is what `eval_answers.py` is for.

## Judging the answers

Retrieval being right doesn't make the answer right. `eval_answers.py` asks a second model to read each answer and say whether it holds up.

```
python eval_answers.py
```

The same 16 questions, plus four the manual genuinely can't answer, each run twice — once with RAG, once without — and every answer graded on three things:

* **correct** — does the answer match what the manual actually says?
* **grounded** — does every claim trace back to the chunks that were retrieved, or did the model fill gaps from memory?
* **declined** — on the questions the manual can't answer, did it say so instead of inventing a plausible number?

Running both ways is the point. The "Use RAG" toggle in the UI shows you one anecdote at a time; the two columns here turn it into a number, and the no-RAG answers are usually confident and wrong in exactly the way the toggle is meant to demonstrate.

The judge is `claude-opus-5`, deliberately a tier above the `claude-haiku-4-5` that writes the answers — a model grading its own output tends to agree with itself. It returns a structured verdict rather than prose, so there's nothing to parse out by hand, and any answer it rejects gets its reasoning printed underneath the table.

**This one costs money.** `eval.py` runs offline and is free to re-run; `eval_answers.py` is about 80 API calls for a full pass. `--limit N` runs the first N cases and `--no-compare` drops the no-RAG half.

There's also a **"Grade this answer" toggle** in the UI, next to the RAG one. Turn it on and the same judge grades your answer live, which is the fastest way to watch a confident no-RAG answer get marked down.

What this doesn't do: check citations. The judge reads whether the claims are supported, not whether the page number printed next to them is the right one.

## Notes

* Model is `claude-haiku-4-5` for speed and cost. Swap it in `rag.py` if you want better answers.
* Scanned manuals won't work. The text has to be real text in the PDF, not an image of text — `ingest.py` will tell you if it finds nothing.
* Chunk size and retrieval count (`k=4`) are hardcoded and worth tuning if answers feel thin.
